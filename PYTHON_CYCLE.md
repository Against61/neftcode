# Цикл решения на Python

Требуется Python 3.12 и NumPy из `requirements-cycle.txt`. Node.js, браузер
и ML-модели для вычисления решения не требуются.

```bash
python3 -m venv .venv-cycle
source .venv-cycle/bin/activate
python -m pip install -r requirements-cycle.txt
python scripts/run_decision_cycle.py --preset bridge --output /tmp/neft-cycle-example
```

В новом каталоге появятся `decision.json` и статическая карточка `report.html`.
Существующий каталог не перезаписывается. Для другого запуска задайте новый
путь. Предустановленные сценарии: `base`, `bridge`, `limited-stock`, `no-clean`,
`sulfur-rise`, `cetane`, `missing`.

Для собственного сценария сохраните `input` из JSON решения в отдельный файл,
измените значения и выполните:

```bash
python scripts/run_decision_cycle.py --input request.json --output /tmp/neft-cycle-custom
```

API: `from neft.decision_cycle import run_cycle, example_request`.
`run_cycle(example_request('bridge'))` возвращает тот же словарь решения,
который CLI сохраняет в JSON. Словарь входа не изменяется.

## Контракт входа

- `schema`: `python-cycle-v1`.
- `scope`: `synthetic_model` или `historical_replay`. Второй режим выдаёт
  `ABSTAIN_HISTORICAL_SCOPE`: реальная телеметрия не отображена автоматически
  на модель действий. Это режим инспекции, не разрешение управлять процессом.
- `origin`: ISO-время в общей локальной шкале источников без UTC offset.
- `state`: все поля примера, без неявного заполнения отсутствующих значений.
  Сера сырья — массовые проценты, сера компонентов/продукта — мг/кг,
  температура — °C, расход — т/ч, запасы — т, давление модели — МПа.
  `sulfur_limit` обязан быть ≤10. Более строгий предел разрешён, ослабление
  через state/JSON/дополнительные поля отклоняется.
- `observations`: необязательные записи с `id`, `source`, `field`, `value`,
  `unit`, `event_time`, `provenance`, сведениями о доступности.
- `bindings`: обязательные привязки конкретных полей модели к наблюдениям
  того же поля/единицы, например `{"crude_sulfur":"crude_sulfur"}`.
  Если доступного наблюдения нет, цикл отказывает; ручного fallback нет.
  `product_sulfur` — наблюдаемый результат; его нельзя привязать к сырью.
- `use_lims_upper_bound`: строго boolean, по умолчанию false. Включение
  допускает sample+4ч по сообщённому максимуму эксперта; это не реальное
  время публикации каждой записи.

ЛИМС: `event_time` — время отбора; `available_time` — явно известная публикация.
`received_time` может дополнительно отложить доступ. Если публикация неизвестна,
без включения правила4ч запись не используется. ПАК дополнительно требует
`event_time_basis="confirmed_measurement"`, `health="healthy"` и явного
`available_time`; таких сведений в имеющемся архиве нет. Виртуальный источник
требует явного времени доступности и `dependencies_available=true`; этот флаг
является входным свидетельством, не независимой проверкой вычисления ВАК.

Приоритет ЛИМС → ПАК → virtual действует только среди допустимых записей
одного поля/единицы; внутри источника выбирается последняя проба. Возраст
считается от измерения/пробы. Политика свежести24ч/1ч/1ч — заданное правило
демонстрации, не подтверждённый регламент установки. Расхождения отмечаются,
их величина не объявляется доказательством поломки. Источник и единица поля
должны быть согласованы вызывающей стороной; в этом этапе испытаны синтетические
записи, не производственное отображение сырья на модель.

## Результат и проверки

`trace` содержит сообщения состояния, качества, нагрузки, оптимизации,
независимого gate и решения с идентификаторами зависимостей. `full` — полный
набор972 сочетаний; `delay_le_1` — отдельная условная диагностика486 сочетаний.
Внешний `recommendation` содержит только допустимый план исходного заказа
из полного набора. Переносы и условные планы не повышаются до рекомендации.
`NO_CHANGE` сохраняет текущий полный рецепт, если он допустим и отличается
по верхней оценке стоимости от оптимума не более чем на1e-6 относительно.

```bash
python -m unittest -v test_decision_cycle test_expert_contracts test_scenario_sensitivity
```

Внутренний parity-аудит сопоставлял семь frozen-пресетов, все интервалы/переносы, планы,
затраты, качество и балансы. Gate отдельно вычисляет скалярные показатели
во всех мирах из команд и входа; не доверяет сохранённому флагу допустимости.
CLI отказывает при неоднозначных ключах JSON и нечисловых/бесконечных входах.
Код0 CLI означает, что решение сохранено; отказ модели отражён в `status`,
это нормальный исход, а не ошибка запуска.

## Ограничения

Собственная модель и конечная сетка унаследованы от v3: фиксированный выход
АВТ, одна команда ГТ, нет пополнения запасов, реальные коэффициенты/лаги не
известны. Практическое качество прогноза не улучшалось. Физический эффект
и промышленная безопасность не установлены. Сам модельный цикл не читает архив.
Его [исторический адаптер](HISTORY_ADAPTER.md) отдельно читает CSV/XLSX,
проверяет происхождение/доступность и формирует historical_replay-запрос.
Связь всех исторических входов с моделью действий остаётся незавершённой.
[Единая консоль](OPERATOR_CONSOLE.md) теперь даёт живой пересчёт через этот API:
архивный контекст отделён от явных модельных допущений, а из истории может
привязываться только допустимый входной T95. Это не историческая валидация.
