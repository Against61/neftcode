# Агент → JSON → расчётный инструмент

Локальный MCP-сервер без архива предоставляет два инструмента:

- `get_refinery_contract({})` — точная схема, единицы/допущения, синтетический
  пример входа и правила работы с анализами.
- `recommend_refinery_plan({"request": ...})` — полный JSON для существующего
  Python-цикла; ответ с основной рекомендацией или отказом, диагностикой,
  идентификаторами и путями доказательств.

При явном подключении локального архива добавляются `get_refinery_history` и
`evaluate_refinery_scenario_with_history`:
[инструкция адаптера](HISTORY_ADAPTER.md). Он возвращает проверенное историческое
состояние и причины отказа от рекомендации. Второй считает отдельный модельный
сценарий с provenance всех входов по [контракту консоли](OPERATOR_CONSOLE.md).
Пути задаются при запуске сервера.

Если оператор также передал hash-pinned bundle, сервер добавляет
`get_refinery_historical_intelligence`. Он возвращает прогноз серы с
эмпирическим диапазоном и исторически типичные P8/T11/F19. Готовый
пакет из `models/` не хранит строки обучения; пять аналогов возвращает локально
пересобранный full bundle.
Ответ остаётся диагностическим: `recommendation=null`, типичные controls нельзя
копировать в оптимизатор как команды. Обучение и подключение описаны в
[HISTORICAL_INTELLIGENCE.md](HISTORICAL_INTELLIGENCE.md).

Агент собирает запрос и объясняет результат. Оптимизацию, предел серы≤10,
доступность анализов и независимый gate выполняет Python. Агент не может
передать в инструмент новую модель, путь записи, команду shell или свой
предел проверки. Неизвестные факты и публикацию анализов нельзя выдумывать.
Наличие декларации в JSON само по себе не доказывает её правдивость: реальный
адаптер проверяет отбор и происхождение в зарегистрированном формате;
истинность внешних деклараций и качество рассуждений LLM требуют отдельных проверок.

## Запуск и подключение

Python3.12, зависимости:

```bash
python3 -m venv .venv-agent
source .venv-agent/bin/activate
python -m pip install -r requirements-agent.txt
python scripts/serve_agent_tool.py --audit-root ./agent-calls
```

Сервер использует **stdio**, а не HTTP-порт. Его запускает MCP-клиент;
при ручном запуске он ждёт протокольный JSON во stdin. Логов в stdout нет.

Готовая конфигурация для клиентского приложения:

```bash
python scripts/agent_connection.py --format json
python scripts/agent_connection.py --format codex
```

Команда печатает абсолютные пути именно текущего Python-окружения — запускайте
её после активации окружения с MCP. Первый формат предназначен клиентам,
читающим `mcpServers`; второй — Codex. Постоянная конфигурация не меняется.
Можно сразу открыть отдельную локальную сессию Codex с этим подключением:

```bash
python scripts/agent_connection.py --launch
```

Если есть архив, одна команда автоматически создаст локальный source-config,
проверит готовую prediction-модель по manifest и добавит три исторических
инструмента:

```bash
python scripts/agent_connection.py --data-root /path/to/archive --launch
```

При запуске сохраняется текущая модель Codex, включается read-only sandbox.
Если CLI устарел и не поддерживает вашу модель, укажите совместимый исполняемый
файл через `--codex-command /path/to/codex`. Сервер ограничивает свои
инструменты; остальные возможности клиентского приложения регулируются самим
клиентом. Подключение не добавляется автоматически в уже открытый чат.

## Как агент должен работать

1. Получить контракт. Определить, что пользователь описывает: явно модельный
   сценарий или реальные наблюдения. Пример нельзя выдавать за реальные данные.
2. Составить полный запрос из известного. Время ЛИМС — время пробы;
   публикация — отдельное поле. Правило sample+4ч использовать только явно.
   Неизвестный ПАК исключается; не создавать вымышленные health/available_time.
3. Вызвать расчёт. Для нового входа нужен новый вызов, предыдущий план не переносить.
   Исторический контекст получать отдельным инструментом; использовать прогноз
   качества для основной рекомендации лишь когда весь диапазон ≤10 мг/кг.
4. При MODEL_PLAN объяснить основной план, выпуск, ограничения и модельную
   природу эффекта. При NO_CHANGE объяснить сохранение режима.
5. При отказе назвать причину. Можно запросить недостающие сведения или
   рассчитать явно изменённое пользователем задание; автоматически ослаблять
   предел10, менять исходный заказ или повышать условный план до основного нельзя.

Основная команда находится только в `recommendation`. `conditional_diagnostic`
не содержит команд и явно помечена как дополнительное условие. Полные условные
планы доступны в сохранённом decision.json как диагностика. Периодический
план уже содержит команды/доли/балансы; агент не должен пересчитывать их сам.
Это модельные рекомендации, не разрешение записывать уставки в оборудование.

## Ошибки и журнал

Каждый корректно разобранный вызов получает отдельный `call_id` и каталог:
`arguments.json`, `request.json` (для расчёта), `result/decision.json`,
`result/report.html`, stdout/stderr дочернего процесса, `response.json`,
`manifest.json`. В манифесте — длительность, версия, команда и SHA. Все пути
задаёт сервер. Во время расчёта код и конфигурация проверяются на изменение.

Отказ модели (`INVALID_INPUT`, `ABSTAIN_*`) — обычный результат MCP,
`isError=false`, с `recommendation=null`. Сбой инструмента, превышение
входа256КиБ, таймаут20с, неизвестное имя/лишние аргументы — `isError=true`.
Старый план не возвращается. Сырые неоднозначные, нечисловые или слишком
длинные протокольные строки отбрасываются до SDK; ошибки фиксируются в
`transport-errors.jsonl`. MCP SDK v1 сообщает об ошибке транспортной строки
через error-notification; неверная строка не доходит до расчёта.

Вызовы последовательны. При отмене клиента уже запущенный расчёт может
закончиться и остаться в аудите, но ограничен20с. Это локальный stdio-сервис,
не общедоступный сетевой endpoint. Сервис не читает производственные файлы
и не имеет инструментов изменения кода или управления установкой.

## Проверки

```bash
python -m unittest -v test_agent_tool test_decision_cycle test_expert_contracts test_scenario_sensitivity test_history_adapter test_operator_console test_historical_intelligence test_historical_intelligence_tool test_historical_training
python scripts/check_agent_protocol.py --output /tmp/neft-protocol-new
python scripts/check_agent_raw_protocol.py --output /tmp/neft-raw-protocol-new
python scripts/run_agent_demo.py --output /tmp/neft-real-agent-new
```

Последняя команда запускает реальный Codex с текущей моделью, делает максимум
три запрошенных инструментальных вызова в тестовом сценарии и сохраняет
транскрипт. Ограничение180с обеспечивается процессом запуска; число вызовов
проверяется по транскрипту, а не считается гарантией одного промпта. Вызов
модели использует существующую авторизацию/квоту Codex. Она не нужна серверу
или протокольным тестам. Нет обучения моделей и новых чтений истории.

Откат: завершить сессию, запущенную через `--launch`, или убрать только
добавленную запись MCP из вашего клиента. Python API продолжит работать.

## Основания протокола

Реализация использует закреплённый официальный Python SDK `mcp==1.30.0`,
поддерживаемую ветку v1. Переход на v2 не выполняется автоматически.
[Документация SDK v1](https://py.sdk.modelcontextprotocol.io/v1/),
[подключение MCP в Codex](https://learn.chatgpt.com/docs/extend/mcp?surface=cli),
[неинтерактивная проверка Codex](https://learn.chatgpt.com/docs/non-interactive-mode).
